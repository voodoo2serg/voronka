# Реализованная CRM Соло-PR

Этот релиз добавляет рабочий CRM-кабинет на Next.js по адресу `/crm/` к существующей Voronka. Кабинет использует настоящий FastAPI API и PostgreSQL, а не демонстрационные данные в браузере. Существующий редактор воронок остаётся по `/`.

## Что работает

- Индивидуальный вход по логину/паролю, создание сотрудников владельцем, отзыв доступа и выход. Пароли — scrypt; существующие Telegram-сессии продолжают работать. Восстановление и подтверждение email — одноразовый код через SMTP с STARTTLS.
- Проектная изоляция для прямых API-запросов, списков и экспорта. До 12 активных сотрудников при создании через CRM.
- Клиенты: ручное создание, изменение с защитой от потерянного обновления, поиск, постраничный список, теги, источники, компания, email, телефон, отказ от сообщений.
- Карточка: несколько сделок, этапы, следующие действия и сроки, история ботов, ручные контакты и их результаты. Ответ через существующее подключение ставит автоматический сценарий на паузу.
- Работа с услугами: аудит, менторство, консультация, стратегическая сессия, курс, разработка курса, обучающая сессия, семинар, клуб, архив. Владелец добавляет каталог и цены; шаблоны создаются неактивными и без вымышленных цен.
- Работа по клиенту: задачи, сессии, этапы результата, документы/ссылки и сроки. Это учёт работ, не интегрированный видеосервис или автоматический отправитель напоминаний.
- CSV: UTF-8/Windows-1251, разделитель, сопоставление колонок, предпросмотр ошибок/возможных дублей, импорт до 5000 строк/5 МБ, журнал партии, повтор без дублирования. Возможные совпадения email/телефона пропускаются без автоматического слияния. Неизвестные поля и импортированные ID сохраняются отдельно. Экспорт защищён от интерпретации формул в таблицах.
- Приветственные кампании: черновик с проверкой получателей, явный запуск, дедупликация, пауза/продолжение/отмена, повторная проверка отказа перед отправкой, статусы реального Outbox.
- Прогрев (outreach): партии `OutreachBatch` / получатели, dry_run с Entry-ссылкой на официальный MAX/Telegram бот, дневной лимит 1–50, уважение `stopped`, без Outbox/Campaign; после Start — обычный Identity/inbox. PyMax — заглушка за флагом, см. [OUTREACH.md](OUTREACH.md).
- Telegram/MAX/ВК используют существующие адаптеры. Импортированные ID не превращаются в подтверждённые диалоги. Есть перенос старых реальных контактов ботов в CRM.
- Email-кампании используют SMTP и тот же долговечный Outbox. Для получателя сотрудник отдельно отмечает разрешение в карточке. Ошибка или неизвестный результат не маскируются под доставку; sent означает приём платформой/SMTP, а не прочтение.
- Заказ фиксирует продукт, цену, индивидуально согласованную стоимость с основанием, скидку, промокод и график взносов. Будущая задолженность не считается просрочкой. Владелец подтверждает внешние поступления/возвраты с основанием; повтор операции не создаёт второй факт.
- Промокоды: процентная скидка, генерация кода, лимит заказов, транзакционное резервирование, освобождение при отмене неоплаченного заказа. В этой версии резервы не имеют автоматического TTL — освобождаются явной отменой.
- Robokassa: платёжные ссылки на весь остаток или часть, отдельные тестовые/боевые пароли, проверка ResultURL, сверка суммы, повтор без двойного платежа. Тестовый счёт не записывает рабочие деньги. `SuccessURL` не используется как подтверждение.
- Политика доступа на уровне CRM: назначение ресурса, минимальный процент оплаты, срок. Сертификат дополнительно требует полной оплаты и подтверждения завершения обучения. Это проверка CRM, не уже установленный перехват выдачи сертификатов Chamilo.
- RAGA: запрос черновика из карточки через существующий Gateway с отдельным alias проекта; ответ записывается в историю и клиенту автоматически не отправляется. Запрос выполняется отдельно от worker доставки.

## Запуск

1. Сделать резервную копию PostgreSQL и media. Внести изменения в `.env`, сохранив действующие токены ботов.
2. `docker compose up -d --build`. Docker собирает Next.js и включает статический экспорт в API-образ; сервис migrate применяет миграции 0004–0006 до запуска приложения.
3. `docker compose exec api python -m scripts.create_crm_owner`. Указать логин, email и пароль через интерактивный ввод. Аккаунт привязывается к существующему `OWNER_TELEGRAM_ID`, повторная перезапись владельца не допускается.
4. Открыть `https://ваш-домен/crm/`. Создать проект либо выбрать существующий, проверить подключения в старом редакторе. Кнопка «Из ботов» переносит контакты подключений выбранного проекта.
5. Для почты настроить SMTP с STARTTLS. В «Команда и подключения» добавить Email-подключение; перед email-рассылкой указать разрешение в нужных карточках.
6. Настроить Robokassa в тестовом режиме: `ROBOKASSA_TEST_PASSWORD1/2`, общий login, совпадающий алгоритм хеша в магазине. ResultURL: `https://ваш-домен/api/crm/robokassa/result`.
7. Для реальных продаж настроить фискализацию отдельно в используемой схеме магазина. Адаптер этой версии не передаёт параметр Receipt и не реализует автоматическое создание чеков. Рабочие ссылки отключены до явной настройки `ROBOKASSA_LIVE_READY=1`, `ROBOKASSA_TEST=0` и боевых паролей. Если магазину требуется Receipt в запросе, этот сценарий ещё нужно реализовать: одной переменной готовности недостаточно.
8. RAGA: `RAG_API_URL` — полный URL `/api/gateway/v1/chat/completions`, `RAG_API_TOKEN` — серверный токен, `RAG_PROJECT_MODELS` — JSON `{ "project-uuid": "gateway-alias" }`. Без явного alias проекта запрос отклоняется.

Для локальной сборки: `npm ci --prefix web && npm run --prefix web build`; скопировать `web/out` в `app/crm_static` до запуска FastAPI. Либо использовать Docker-сборку. Запуск одного Next.js dev-сервера без API-прокси не является готовым окружением CRM.

## Ужесточения после CRM-этапа

- `POST /staff` принимает только `manager`/`editor`; единственный owner — через `create_crm_owner` / `OWNER_TELEGRAM_ID`.
- Менеджер видит только назначенных клиентов/сделки (list/detail/export/campaign eligibility); владелец и партнёр — весь проект.
- Отключение сотрудника и смена пароля явно отзывают Redis-сессии; CRM-логин ставит HttpOnly cookie `crm_session` (+ Bearer для совместимости); `/crm/` отдаёт CSP.
- После commit импорта CSV-строки партии очищаются; fingerprint и report сохраняют replay.
- Индикатор Robokassa в обзоре учитывает тестовые или боевые пароли в зависимости от `ROBOKASSA_TEST`.
- Экран «Диалоги» поднимает ответ по существующим API; список grants заказа доступен через `GET /orders/{id}/grants`.

## Что остаётся отдельным этапом реализации

Архитектура PLATFORM_ARCHITECTURE.md шире этого CRM-релиза. Пока не реализованы: публичный продающий сайт по всем текстам, личный кабинет ученика, Keycloak SSO, LMS Adapter/Policy Bridge Chamilo, реальная выдача LMS-сертификатов, защищённое видео/архив, видеопровайдер и автоматическое расписание напоминаний, ЮKassa, регистрация с одобрением владельца, платежи Stars внутри Telegram, автоматическая полная фискализация / параметр `Receipt` в Robokassa. Не выдавать CRM-проверку прав за защиту ещё не подключённой LMS.

Аутентификация этого релиза локальная, как запрошено владельцем для первого этапа. Это переходное решение: при подключении Chamilo учётные записи мигрируются в единый IdP по отдельной процедуре, пароли между приложениями не копируются. Состояние Chamilo в кабинете явно обозначено как «адаптер ещё не реализован».

Не отправлять конфиденциальные документы обычной заметкой со сторонней публичной ссылкой. Медиабанк старой Voronka остаётся отдельным доступным инструментом; единый защищённый документооборот ещё не добавлен.

## Проверка и миграции

- `python -m pytest -q`: серверные тесты, старая воронка и новые CRM-инварианты.
- `npm run --prefix web build` и `npm run --prefix web typecheck`.
- `RUN_BROWSER=1 python -m pytest -q tests/test_crm_browser.py`: production Next.js-export и реальный FastAPI через TestClient, desktop/mobile. API CRM в этих проверках не подменяется готовыми фиктивными ответами.
- В CI: PostgreSQL upgrade/downgrade/upgrade, PostgreSQL HTTP-тесты, Docker и браузеры.
- Реальные токены каналов, SMTP, домен, ResultURL магазина и RAGA проверяются после настройки. Автотесты не доказывают доставку настоящему клиенту.
- Миграция 0005 увеличивает длину адресата Outbox для email; downgrade блокируется при длинных сохранённых адресах, чтобы не потерять данные.
- Миграция 0006 добавляет `crm_outreach_batches` / `crm_outreach_recipients` для warm-up без маршрутизации через Campaign/Outbox.

## Интерфейс

Композиция ориентируется на Twenty: нейтральная боковая навигация, плотная таблица, доска сделок и боковая карточка. Исходный код компонентов Twenty не копировался; зависимости и лицензии его сервера не переносятся в проект.
