# Исправления после архитектурного аудита 27.11.2026

Этот набор изменений подготовлен локально относительно main пяти репозиториев. Он не подтверждает состояние работающего VPS и не выполняет развёртывание автоматически.

## Изменения контрактов

- YooKassa: webhook сверяет объект платежа через аутентифицированный GET API провайдера. Проверяются магазин, сумма, валюта, идентификатор счёта и test/live режим. Только подтверждённый `succeeded` с `paid=true` создаёт Payment; `waiting_for_capture` не выдаёт доступ. `YOOKASSA_ENABLED=0` и тестовый счёт сохраняют только аудит события без изменения денег и состояния счёта. Нельзя включать live без проверки реального provider sandbox и возврата.
- CRM: entitlement фиксируется отдельно от HTTP-доставки. `delivery-site`, `delivery-lms`, `delivery-signal` запускаются отдельными процессами из compose. Каждый удерживает только одну строку своего направления. Основной worker больше не доставляет integration outbox; все три новых процесса обязательны при обновлении.
- Письмо об открытом курсе ждёт `/api/integrations/voronka/enrollment/status` с подтверждённым applied состоянием LMS. До обновления адаптера письма остаются pending. Коммерческий AccessGrant остаётся в CRM; уведомление не является источником права.
- LMS: signed lookup сайта `/api/integrations/solo_pr/enrollment/status`, ключ `LMS_API_SECRET` должен совпадать с ключом сайта. Legacy body-only HMAC выключен по умолчанию (`LMS_ALLOW_LEGACY_HMAC=0`). Известный отправитель CRM уже использует timestamp HMAC.
- Signal: недоступная send-policy повторяется, отсутствие конфигурации не разрешает transactional send. История CRM получает lease и backoff с ограничением попыток. Перед новым кодом необходимо применить Alembic revision `0021`.
- Media Registry: v2 HMAC подписывает метод, raw path/query, digest точного тела и nonce. Nonce хранится в собственной БД и отклоняет повторы. Сервер создаёт таблицу `request_nonces` при startup. Для локальных подписанных ссылок также обязателен `MEDIA_S3_SECRET_KEY`. Изменены клиенты Signal и Voronka; другие потребители требуют проверки.
- Сайт: cron всегда требует CRON_SECRET/OUTBOX_CRON_SECRET; заголовок Host не даёт разрешение. Временные ошибки применения события и загрузки его зависимостей возвращают 503. SQLite в рабочем режиме ожидает блокировку не больше 3 секунд по умолчанию (SQLITE_BUSY_TIMEOUT_MS, предел 10 секунд), повторные циклы остаются только для сборки.
- Запрос удаления сайта атомарно сохраняется в local outbox вместе с удалением данных. CRM принимает его в durable inbox `pending_review` по отдельной подписи сайта. Ответ означает приём запроса, а не завершённое удаление данных всей платформы. Владелец видит очередь через GET `/api/crm/integrations/privacy-requests`. После подтверждённого приёма email удаляется из payload очереди сайта. Правила хранения финансовых документов и завершение обработки остаются ответственностью владельца; автоматического удаления ledger нет.
- Portal больше не подтверждает доступ демонстрационными assignments. Демонстрационные встречи выключены по умолчанию; временное включение LMS_ENABLE_MEETING_STUBS=1 допустимо только для явно тестовой эксплуатации, журнал всё ещё недолговечен.
- Overlay OpenOlat упаковывается из commit в `lms_end/deploy/openolat/chrome-revision`. Старые vendored файлы не являются источником релиза. Совместимый wrapper больше не копирует произвольный текущий checkout.
- CI не зависит от выделенных runners с отсутствующим результатом; добавлены hosted runner, отдельный прогон Media Registry и security contracts сайта. Это изменения workflow, а не утверждение, что GitHub CI уже прошёл на этих локальных файлах.

## Порядок развёртывания

1. Получить утверждённый SSH-доступ и read-only inventory: HEAD/.deploy-sha, image digests, текущие миграции, состав compose, возраст pending/dead/sending очередей. Не выводить env и значения ключей в отчёты.
2. Создать согласованные резервные копии CRM/Signal/LMS PostgreSQL, SQLite сайта и объектов MinIO; проверить восстановление в отдельное окружение. Не удалять volumes и не менять существующие пароли БД простым изменением POSTGRES_PASSWORD: старые volumes сохраняют прежние роли.
3. Сохранить действующие credentials в обязательных переменных Signal compose. Переменные не должны содержать примерные значения из тестов. Если пароль включается в DSN, использовать корректное URL-кодирование. Встроенные ранее пароли администраторов считаются скомпрометированными и требуют смены на работающем сервисе.
4. Обновить LMS adapter первым, проверить signed status и фактическое active/revoked в OpenOlat. Передать сайту и адаптеру одинаковый выделенный LMS_API_SECRET. Проверить, что все реальные отправители используют timestamp HMAC.
5. Обновить Media Registry с временно разрешённым legacy только при необходимости совместимого окна. Обновить оба известных клиента, проверить signed upload, изменение тела и replay, затем выключить MEDIA_ALLOW_LEGACY_HMAC. Не оставлять переходный флаг включённым. Провести такой же переход для других реальных потребителей, если они обнаружены.
6. Применить Signal migration 0021, затем обновить API и worker. Проверить восстановление history после отключения CRM и отсутствие повторной отправки самих писем.
7. Обновить CRM и запустить основной worker вместе с тремя delivery-сервисами. Проверить отдельные queue metrics и heartbeat `worker:integration:<destination>`. Сбой одного delivery не должен останавливать остальные направления.
8. Обновить сайт, настроить cron secret, проверить 400 для некорректного события, 503 при временной блокировке и успешный повтор. Bootstrap требует BOOTSTRAP_CMS_PASSWORD/BOOTSTRAP_OPS_PASSWORD/BOOTSTRAP_COMMUNITY_PASSWORD, не меняет существующие пароли без BOOTSTRAP_ROTATE_PASSWORDS=1.
9. Подготовить overlay через `bash scripts/prepare_openolat_chrome.sh . ../openolat-solo-pr` в lms_end, затем использовать штатный deployment script. Проверить revision.txt и реальные страницы learn.
10. Сквозной прогон: регистрация, дубликат оплаты, delayed LMS, подтверждённый курс, письмо, частичный/полный возврат, regrant, устаревшая revision, progress, timeline, запрос удаления. Сверить deployed manifest всех пяти репозиториев.

## Что не закрывается локальным кодом

Единственный VPS и общий ресурс PG LMS/Keycloak/OpenOlat остаются инфраструктурными точками отказа. Нужны согласованные RPO/RTO, резервная площадка/восстановление, мониторинг и проверенный runbook. Фактические MFA владельца, Mailu antivirus, доставляемость писем, остаточные учётные записи и истёкшие media-флаги проверяются в runtime. Большие UI-файлы и архивные копии требуют отдельного планового разделения; их механическое удаление не является безопасным исправлением. Остальные эвристические high Floorplan необходимо квалифицировать по реальной авторизации, а не автоматически считать публичными write API.

## Откат

Сохранить предыдущие image digests, настройки и manifest до обновления. При ошибке остановить affected delivery/worker, сохранив durable очереди; вернуть согласованный комплект приложений. Нельзя откатывать новые поля Signal до остановки использующих их workers. Не откатывать усиление платежного подтверждения включением доверия к входящему JSON. Не применять down -v и не очищать очереди для восстановления зелёного health.
