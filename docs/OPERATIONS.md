# Эксплуатация сервера

## Компоненты

| Компонент | Сейчас | Назначение |
|---|---|---|
| Debian 13 или Ubuntu 24.04 LTS | Требуется на сервере | ОС |
| Docker Engine и Compose plugin | Требуются | Запуск контейнеров |
| Caddy или существующий nginx | Профиль edge либо vhost | HTTPS, прокси |
| FastAPI | В Compose | API, Mini App, webhook |
| PostgreSQL 16 | В Compose | Контакты, сценарии, очереди, таймеры |
| Redis 7 | В Compose | Административные сессии |
| Python worker | В Compose | Движок и доставка |
| Alembic | Одноразовый migrate | Миграция перед запуском |
| Docker volume media | В Compose | Закрытый медиабанк |
| MinIO или внешнее S3 | При росте объёма | Распределённое хранилище |
| FFmpeg/FFprobe | В Docker-образе | Проверка формата загрузок |
| Celery | При масштабировании | Опциональный диспетчер фоновых работ |

На первом сервере дополнительных LLM, Qdrant, LangGraph и Kubernetes не требуется. Система может работать рядом с RAGA, но должна иметь отдельную БД, каталоги, бот-токены и порт/домен.

## Доступ

Внешние порты: 80/443 и ограниченный SSH. PostgreSQL/Redis/API — только сеть Compose. Firewall сервера должен разрешать административный SSH только выбранным адресам либо через установленный безопасный канал доступа.

Файл .env не коммитить, права файла ограничить владельцем сервера. После изменения окружения пересоздать API и worker. Помощница вводит содержание в панели, токены ей не требуются. Назначение прав не означает предоставление SSH.

Административный бот не имеет webhook-обработчика бизнес-сценариев: он открывает Mini App через меню. Его токен используется только для проверки Telegram-входа и настройки меню. Пользовательские боты имеют свои webhook и токены.

## Проверки после запуска

1. GitHub Actions должен пройти тесты и миграции.
2. HTTPS домен открывается без ошибки сертификата.
3. /health отвечает ok: PostgreSQL, Redis и свежий пульс worker. Без worker ответ 503.
4. Основной владелец входит; посторонний Telegram ID получает отказ.
5. Помощница видит только выделенные подключения; попытка API-запроса к чужому connection_id получает 403.
6. Бот отправляет тестовый пост в разрешённый тестовый канал.
7. Ссылка приводит в правильную воронку; source записан в journal.
8. Повторный webhook не создаёт второй запуск.
9. PDF не отправляется до завершения всех вопросов.
10. Перезапуск worker не теряет ожидание.
11. /stop останавливает текущую воронку.
12. Ручной ответ менеджера приостанавливает автоматизацию.
13. Доставка с неизвестным результатом требует ручной проверки.
14. Проверить восстановление БД из копии на отдельном тестовом экземпляре.

## Обновление

Перед обновлением сделать копию БД и сохранить текущий commit. Проверить миграции на копии; затем обновлять код и запускать Compose. В baseline изменение schema требует новой Alembic revision; замороженную schema_v1 не менять. Не запускать downgrade на рабочей БД: он удаляет данные.

Команды:
- docker compose ps
- docker compose logs --tail=100 worker
- docker compose logs --tail=100 api
- sh scripts/backup.sh

Приложение намеренно не печатает URL запросов с бот-токенами. Не включать подробное HTTP-логирование библиотек без маскирования credentials. Тексты ответов в БД доступны уполномоченным администраторам.

## Резервные копии

Ежедневный pg_dump, копия вне сервера, шифрование и отдельный ключ восстановления. Рекомендуемая политика: 7 дневных, 4 недельных, 3 месячных; это предлагаемые параметры, а не настроенная автоматизация.

Redis можно восстановить без бизнес-данных: пользователи повторно войдут в админку. PostgreSQL терять нельзя. Скрипт backup.sh сохраняет БД и media volume. Он временно останавливает API/worker для согласованной копии и запускает их обратно. После добавления S3 резервировать и объектное хранилище.

## Ограничения эксплуатации baseline

Один worker с advisory lock и heartbeat. Есть отложенный повтор явного 429, закрытый media volume и проверка формата загрузок. Массовые рассылки, автоматический повтор неизвестного сетевого результата, антивирусный анализ и платежи не реализованы. Административный вход работает через Mini App; отдельный вход в обычном браузере не реализован. В панели доступны pause/resume/stop для отдельных участников. Операция массовой остановки не реализована.

Перед производственным использованием нужны нагрузочная проверка, мониторинг возраста очереди/ошибок webhook и ротация секретов. Для MAX отдельно проверить trust store и успешность настоящего HTTPS-соединения. Не обходить ошибки сертификата через verify=False.

## Рабочий запуск Telegram

В панели выполните проверку готовности: database, redis, media_writable, worker_alive должны быть true. Затем активируйте webhook подключения; меню административного бота настраивается scripts.register admin. Для callback-кнопок нужны события callback_query. Для MAX включены message_callback; TLS-проверку не отключать.

Для медиа загрузите MP4/PDF, отправьте себе тестовое сообщение, проверьте sent и наличие файла в пользовательском боте. После этого опубликуйте воронку из шаблона и пройдите её другим аккаунтом. При обновлении с предыдущей версии применяется миграция 0002; volume media сохранять. Python-зависимости зафиксированы в constraints.txt.

## CRM: боевые платежи Robokassa и фискализация

Перед `ROBOKASSA_LIVE_READY=1` и `ROBOKASSA_TEST=0` обязательно:

1. Магазин Robokassa настроен в нужном режиме (тест или бой) с паролями `#1/#2` и алгоритмом хеша, совпадающим с `ROBOKASSA_HASH`.
2. **Фискализация решена явно:** либо чеки формируются в личном кабинете/схеме магазина Robokassa без передачи `Receipt` из Voronka, либо отдельная доработка адаптера с параметром `Receipt` уже внедрена. Текущий CRM-адаптер **не передаёт** `Receipt` и не создаёт чеки сам.
3. ResultURL указывает на `https://ваш-домен/api/crm/robokassa/result` и отвечает `OK{InvId}` на проверочные уведомления.
4. На staging прогнан тестовый платёж (`ROBOKASSA_TEST=1`): ссылка открывается, ResultURL проходит, в обзоре CRM индикатор Robokassa зелёный для тестовых паролей.
5. Есть решение владельца в письменном виде (тикет/заметка), что живые деньги допустимы без автоматического `Receipt` из API **или** что `Receipt` уже реализован.

Без пунктов 2 и 5 **не включать** `ROBOKASSA_LIVE_READY`. Индикатор в обзоре CRM отражает готовность текущего режима (тест vs live), а не «магазин готов к продажам».

## CRM: сессии и XSS

Кабинет `/crm/` отдаёт CSP (`default-src 'self'`, без сторонних скриптов). Сессия CRM ставится HttpOnly-cookie `crm_session` (SameSite=Lax) и дополнительно возвращает Bearer-токен для совместимости. Отключение сотрудника и смена пароля явно отзывают Redis-сессии. `CRM_COOKIE_SECURE=0` допустим только на локальном HTTP.

## CRM: прогрев (outreach) и неофициальные аккаунты

Политика: личные аккаунты (PyMax / userbot) **не** являются Connection для кампаний и **не** пишут в Outbox ботов. Chatwoot и EspoCRM в стек не входят — inbox и сделки остаются в voronka.

1. Создайте/опубликуйте воронку и Entry на **официальном** Telegram или MAX боте проекта.
2. В CRM выберите клиентов с телефонами → «Прогрев (dry_run)» → подготовьте тексты и deep link.
3. Отправку с отдельной SIM выполняйте вручную (или будущим адаптером); отметьте outcome в партии.
4. После Start пользователя Identity и «Диалоги» работают как обычно.

Ограничения: `daily_cap` ≤ 50; `OUTREACH_MAX_ENABLED` по умолчанию `0`. Не смешивать боевой личный номер владельца бренда с warm-up SIM. Подробности — [OUTREACH.md](OUTREACH.md). Миграция `0006` добавляет таблицы партий.
